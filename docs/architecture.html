Arquitectura

Cómo está armado el pipeline, y por qué

Ariadne tiene un pipeline lineal, sin estado compartido raro: cada fase lee lo que necesita y produce datos inmutables para la siguiente.

walk (respeta .gitignore)
  → classify (extensión, lenguaje, ícono, ¿es generado?, categoría, forma)
  → extract imports / extract classes / collect git history
  → build_graph (arma nodos + aristas Contains/DependsOn, resuelve referencias)
  → render (html interactivo, o markdown → Pandoc → pdf/rtf/xml/latex)

src/extractor/build_graph.rs es el corazón: el único lugar donde todas las fases anteriores se juntan en un Graph (src/schema/mod.rs), una lista plana de GraphNode/GraphEdge, no un árbol. El árbol que ves en el diagrama lo reconstruye el cliente (client/src/data.ts::buildFilteredTree) a partir de parent_id, aplicando filtros y colapsos. Esa decisión, mandar un grafo plano y dejar que el cliente arme la vista, es la razón por la que agregar clases, métodos, atributos, o una estrella de documentación, nunca tocó una sola línea de renderizado del árbol: todo lo que necesita parent_id, depth y un node_type reconocido ya se renderiza solo.

Por qué usa heurística de texto en vez de un parser AST real

Cada extractor (imports.rs, classes.rs) reconoce patrones de texto por línea o por bloque, sin un parser real de ningún lenguaje. Es una decisión de diseño, no una limitación temporal: soportar 15 lenguajes con parsers AST reales significaría mantener 15 gramáticas y dependencias distintas, cada una con su propio ciclo de breaking changes. La heurística de texto es barata de escribir, barata de extender, y falla de forma predecible: macros, metaprogramación, o formato muy poco convencional pueden romperla, y eso se documenta explícitamente en cada función en vez de prometer una precisión que no existe.

Por qué un grafo plano en JSON en vez de un árbol anidado

El JSON embebido (<script type="application/json" id="ariadne-graph-data"> en el HTML generado) es intencionalmente la forma más simple posible: nodes/edges planos, sin anidar. Hay dos razones:

  • El cliente necesita reconstruir vistas distintas del mismo grafo (colapsado, filtrado por extensión, sin generados, etc.). Tener un árbol ya armado de un lado específico obligaría a reconstruirlo de todos modos cada vez que cambia un filtro.
  • Un agente de IA que lea este JSON directamente, en vez de mirar el dibujo, puede recorrer nodes/edges con cualquier herramienta común sin entender la lógica de árbol del cliente.

El HTML de salida es un solo archivo autocontenido

El bundle de JS (D3 compilado por esbuild), los datos del grafo, el sprite de íconos SVG y el favicon (como data URI) van todos embebidos en el mismo .html. Cero requests externos, funciona abierto con file:// o subido tal cual a GitHub Pages. Por eso "ver historial" muestra como máximo 5 commits precalculados al generar, en vez de pedirle nada a git en vivo: no hay ningún servidor corriendo cuando alguien abre el HTML.
